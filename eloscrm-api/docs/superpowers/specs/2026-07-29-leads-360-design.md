# Leads 360 — Spec de Design

> Aprofundamento de **leads/clientes** no elosCRM até o nível de um Kommo/Pipedrive: histórico de tudo
> que aconteceu, comentários da equipe, anexos privados e um cadastro que descreve o lead de verdade.

Estado de referência: commit `74ff0d5`, mais o trabalho em andamento de storage (`src/lib/storage.ts`,
envs `R2_*`, `@aws-sdk/*` no `package.json`) que ainda não está commitado.

---

## 1. O que existe hoje

| Peça | Estado |
|---|---|
| `Client` | `name`, `email`, `phone`, `source`, `notes`, `ownerId` (String solto, sem relação) |
| Tela do lead | `app/(app)/clients/[id]/` com abas Resumo · Atividades · Visitas · Propostas · **Arquivos (placeholder vazio)** |
| "Linha do tempo" | `ActivityTimeline` — lista **só** `Activity`, ordenada por `doneAt ?? dueAt ?? createdAt` |
| "Responsável" | Card fixo com `—` (`page.tsx:160-167`): `ownerId` não resolve para nome nenhum |
| Histórico de mudanças | **Não existe.** Trocar estágio, dono ou valor não deixa rastro |
| Comentários | **Não existem.** `notes` é um campo único, sobrescrito, sem autor nem data |
| Anexos | **Não existem.** `Property.photos String[]` é o único campo de arquivo, e guarda URL solta |
| Storage | `src/lib/storage.ts` já pronto (presign PUT/GET, head, delete, bulk delete) — **não commitado** |

### Os três buracos que doem

1. **Nada é auditável.** Um negócio que voltou de "Proposta" para "Contato" não tem como ser explicado.
   Num CRM multiusuário isso é o mínimo — é o que responde "quem mexeu nisso e quando".
2. **A timeline mente por omissão.** Ela se chama "linha do tempo" mas só mostra atividades; mudança de
   estágio, comentário e anexo não aparecem. O usuário lê o cartão e acha que nada aconteceu.
3. **O lead é raso.** `notes` como campo único não sobrevive a duas pessoas trabalhando o mesmo lead:
   quem edita por último apaga o contexto do outro.

## 2. Decisões

| # | Decisão | Por quê |
|---|---|---|
| D1 | Auditoria em **tabela única** com `entityType` + `entityId`, ligada em Client, Deal, Property e Activity | Uma escrita, um índice, um endpoint. Ligar numa entidade nova depois é uma linha |
| D2 | **Sem FK** de `entityId` para as tabelas de domínio | Uma FK por tipo obrigaria uma coluna por tipo; e o histórico precisa sobreviver ao delete da entidade |
| D3 | Ator gravado como **snapshot** (`actorId` + `actorName`), não como relação com `User` | O nome no histórico é o que era na hora do fato. Evita join e sobrevive ao membro sair da imobiliária |
| D4 | `actor` entra como **último parâmetro explícito** das funções de escrita dos services | O projeto passa `orgId` explícito e não usa `AsyncLocalStorage`; manter o mesmo estilo |
| D5 | Anexos com o mesmo par `entityType`/`entityId` da auditoria | Documento do comprador no cliente, proposta no negócio, matrícula no imóvel |
| D6 | Bucket **sempre privado**; toda leitura por presigned GET de vida curta | Requisito explícito. Nenhuma URL pública, nenhum objeto legível sem assinatura |
| D7 | Upload direto do browser para o R2 via presigned PUT | O arquivo não passa pela API: sem limite de body, sem custo de banda dupla |
| D8 | `Property.photos String[]` **fica como está** | É vitrine (pública por natureza). Anexo é documento privado. Misturar os dois obrigaria migração sem ganho |
| D9 | Timeline unificada montada **em memória** a partir das 4 fontes | Volume por lead é dezenas de itens, não milhares. Cursor real sobre 4 tabelas não se paga aqui |
| D10 | Comentários **sem menção/notificação** | Menção sem notificação é enfeite; notificação é outro subsistema (e-mail/push) fora deste escopo |

### D11 — Confirmação de upload é `HEAD` de verdade

O fluxo é `upload-url` → PUT do browser → `confirm`. O `confirm` chama `headFile()` no R2 e só marca
`READY` se o objeto existir, gravando o `size` real que o storage reporta.

A alternativa (confiar no cliente) deixaria linha `READY` apontando para objeto inexistente sempre que o
PUT falhasse depois do `upload-url`. **Consequência para os testes:** `attachments.test.ts` precisa de um
S3 real. Em dev/CI aponta-se `R2_ENDPOINT` para o SeaweedFS local (`http://localhost:8333`), que é
S3-compatível e já roda na máquina; no CI isso vira um service container. Anexo `PENDING` que nunca
confirma vira lixo silencioso — a limpeza é um follow-up nomeado, não faz parte deste escopo.

## 3. Modelo de dados

Tudo em `prisma/schema.prisma`. **Verificado:** `pnpm auth:generate` faz *merge* — rodei com um campo
removido do `User` e o CLI restaurou só aquele campo, preservando todos os models de domínio. Adicionar
models aqui é seguro; ele apenas reposiciona campos que ele mesmo gerencia.

```prisma
enum AuditEntity {
  CLIENT
  DEAL
  PROPERTY
  ACTIVITY
}

enum AuditAction {
  CREATED
  UPDATED
  DELETED
  STAGE_CHANGED
  OWNER_CHANGED
}

enum LeadTemperature {
  FRIO
  MORNO
  QUENTE
}

enum AttachmentStatus {
  PENDING
  READY
}

model AuditEvent {
  id             String       @id @default(cuid())
  organizationId String
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  entityType     AuditEntity
  entityId       String
  action         AuditAction
  actorId        String?
  actorName      String?
  // { campo: { from, to } } — só os campos que mudaram
  changes        Json?
  createdAt      DateTime     @default(now())

  @@index([organizationId, entityType, entityId, createdAt])
}

model Comment {
  id             String       @id @default(cuid())
  organizationId String
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  entityType     AuditEntity
  entityId       String
  authorId       String
  authorName     String
  body           String
  editedAt       DateTime?
  createdAt      DateTime     @default(now())
  updatedAt      DateTime     @updatedAt

  @@index([organizationId, entityType, entityId, createdAt])
}

model Attachment {
  id             String           @id @default(cuid())
  organizationId String
  organization   Organization     @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  entityType     AuditEntity
  entityId       String
  // chave no bucket privado: org/<orgId>/<entityType>/<entityId>/<cuid>-<slug>
  key            String           @unique
  filename       String
  contentType    String
  size           Int
  status         AttachmentStatus @default(PENDING)
  uploadedById   String
  uploadedByName String
  createdAt      DateTime         @default(now())

  @@index([organizationId, entityType, entityId, createdAt])
}
```

Campos novos em `Client` (fase B):

```prisma
model Client {
  // ... campos atuais
  description String?          // texto longo, markdown simples
  tags        String[]         // livre, por organização
  temperature LeadTemperature  @default(MORNO)
  interestType String?         // "Apartamento", "Casa", "Terreno"…
  budgetMin   Decimal?
  budgetMax   Decimal?
}
```

`notes` **continua existindo** — vira o campo curto de recado interno; `description` é o texto do perfil
do lead. Renomear obrigaria migração de dados sem ganho.

`Organization` ganha os campos inversos: `auditEvents AuditEvent[]`, `comments Comment[]`,
`attachments Attachment[]`.

## 4. Contratos de API

Tudo sob `/v1`, com `authGuard` + `orgGuard` por arquivo de rota (o padrão do projeto: rota sem os hooks
fica **aberta**).

### Auditoria — leitura

```
GET /v1/audit-events?entityType=CLIENT&entityId=<id>&limit=50
→ 200 [{ id, entityType, entityId, action, actorId, actorName, changes, createdAt }]
```

Sem POST: evento de auditoria só nasce de dentro dos services.

### Diretório de membros

```
GET /v1/members
→ 200 [{ userId, name, email, role }]
```

Resolve `ownerId` para nome sem criar relação Prisma com `User` (D3) e alimenta o select de responsável.

### Comentários

```
GET    /v1/comments?entityType=CLIENT&entityId=<id>
POST   /v1/comments        { entityType, entityId, body }              → 201
PATCH  /v1/comments/:id    { body }                                     → 200  (só o autor; grava editedAt)
DELETE /v1/comments/:id                                                 → 204  (só o autor ou owner/admin)
```

### Anexos

```
POST /v1/attachments/upload-url
  { entityType, entityId, filename, contentType, size }
  → 201 { attachmentId, uploadUrl, key, expiresIn }

POST /v1/attachments/:id/confirm      → 200 { …attachment, status: "READY" }
GET  /v1/attachments?entityType&entityId → 200 [ …attachments READY ]
GET  /v1/attachments/:id/download-url → 200 { url, expiresIn }
DELETE /v1/attachments/:id            → 204  (apaga objeto no R2 e a linha)
```

Limites validados no `upload-url`: `size` ≤ 20 MB e `contentType` numa allowlist (PDF, PNG, JPEG, WEBP,
DOCX, XLSX). Presign de upload expira em **300s**; o de download em **60s**.

### Timeline unificada

```
GET /v1/clients/:id/timeline?limit=50
→ 200 [ { kind, at, ...payload } ]   // desc por `at`
```

`kind` ∈ `ACTIVITY | AUDIT | COMMENT | ATTACHMENT`. Busca `limit` de cada fonte, funde em memória, ordena
e corta em `limit` (D9). `limit` máximo 100.

## 5. Pré-requisitos de infraestrutura

**CORS do bucket R2** — sem isso o PUT do browser falha com erro opaco de CORS, não com 4xx útil:

```json
[{
  "AllowedOrigins": ["http://localhost:3000", "https://<host-do-web-em-producao>"],
  "AllowedMethods": ["PUT", "GET"],
  "AllowedHeaders": ["content-type"],
  "ExposeHeaders": ["etag"],
  "MaxAgeSeconds": 3600
}]
```

**Envs** (`R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_PRIVATE_BUCKET_NAME`) já estão
em `src/env.ts` como **obrigatórias**. Precisam existir em `.env`, `.env.example`, `.env.test`,
`.env.test.example` e no job `api` do `.github/workflows/ci.yml`. Hoje faltam em todos menos no `.env` —
a suíte inteira falha no boot com `Invalid environment variables`.

**Estilo do `src/lib/storage.ts`** — o arquivo está com aspas simples e sem ponto e vírgula, divergindo do
resto da API. Não há Prettier no projeto; alinhar na mão ao aplicar o plano C.

## 6. Fatiamento em três planos

Cada fase entrega software funcionando por conta própria.

| Plano | Entrega | Depende de |
|---|---|---|
| **A — Contexto e auditoria** | `.env.test`/CI destravados, `Actor` nos services, `AuditEvent` nas 4 entidades, `GET /v1/audit-events`, `GET /v1/members`, aba **Histórico** na tela do lead com nome do responsável resolvido | — |
| **B — Cadastro e comentários** | `description`, `tags`, `temperature`, `interestType`, `budgetMin/Max`; CRUD de comentários; UI de perfil e mural | A (usa `actor` e audita as mudanças) |
| **C — Anexos e timeline** | Anexos privados no R2 (presign PUT/GET), aba **Arquivos** de verdade, `GET /clients/:id/timeline` fundindo as 4 fontes | A e B (a timeline só faz sentido com as 4 fontes existindo) |

O plano A está escrito por inteiro em
[`plans/2026-07-29-leads-360-a-auditoria.md`](../plans/2026-07-29-leads-360-a-auditoria.md).
B e C ganham plano próprio quando A estiver em produção — o modelo de dados dos três já está decidido
aqui, então nada bloqueia.

## 7. Fora de escopo (nomeado, não esquecido)

- **Menções e notificações** em comentários (D10)
- **Campos customizados por organização** ao estilo Kommo — exige tabela de definição, render dinâmico e
  validação em runtime; é um subsistema inteiro
- **Faxina de anexos `PENDING`** que nunca confirmaram (D11)
- **Versionamento de anexo** (substituir arquivo mantendo histórico)
- **Retenção/expurgo do audit log** — a tabela cresce para sempre; quando incomodar, particionar ou
  arquivar por data
